## Findings — severity | file:line | what breaks | how to reach it | fix


**LOW | `frontend/src/components/ScoreForm.tsx:177` vs `backend/app/services/evaluation.py:222,248` | Preview and stored result can differ by 0.1 in the number that ends up in the hashed legal PDF.** The comment at ScoreForm.tsx:182 claims “قرینهٔ دقیقِ `evaluation.compute_result`”, but the two use different rounding semantics: JS `round1 = Math.round(v*10)/10` is half-up; Python `round(x, 1)` is half-to-even. Demonstrated: `round(84.25, 1) → 84.2` (Python) vs `84.3` (JS); ties like 83.75 happen to agree, so the bug is intermittent and will look like a fluke when reported. Concrete path: unit_supervisor opens the scoring form; section pcts come out 90.0 and 78.5 with equal section weights (ordinary integer-score sums, e.g. 18/20 and 157/200) → `base_pct = round((90+78.5)/2, 1)`; the live preview shows **84.3**, the evaluator confirms at that number, server stores **84.2**, and 84.2 is what HR, the CEO, and the QR-verifiable PDF show. Same divergence exists at the first-stage roundings (line 222/223 server, 178/179 client). Fix: make one side the definition of the other — either port half-even into `round1` (e.g. `const r = v*10; const f = Math.floor(r); const diff = r - f; if (diff !== 0.5) return (diff < 0.5 ? f : f+1)/10; return (f % 2 === 0 ? f : f+1)/10;`) or switch the server to explicit half-up (`Decimal(str(x)).quantize(Decimal('0.1'), rounding=ROUND_HALF_UP)`); add a parity test that feeds tie values (0.25/0.75-ending pcts) through both implementations.
