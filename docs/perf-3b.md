# فازِ ۳ب و ۳پ — عددها

نقشهٔ راه برای این فاز یک قاعده گذاشت:

> **اندازه‌گیری پیش از تغییر:** ۳ب و ۳پ بدونِ عدد انجام نشوند. یک دیتابیسِ
> پرشده با داده‌های ساختگیِ سه‌ساله بسازید، اندازه بگیرید، بعد تغییر دهید، بعد
> دوباره بگیرید. بدونِ آن نمی‌شود گفت بهتر شد یا فقط عوض شد.

این فایل همان عددهاست — هم آن‌جا که تغییر داد، هم آن‌جا که نشان داد تغییر
لازم نیست.

## چطور دوباره ساخته شود

```bash
createdb nexahr_load
export DATABASE_URL=postgresql://nexahr:…@localhost:5432/nexahr_load
cd backend
alembic upgrade head
python -m scripts.seed_load_test --personnel 1000 --years 3
python -m scripts.measure_hot_paths --repeats 5          # جدول
python -m scripts.measure_hot_paths --only "جارو" --trace # پرتکرارترین کوئری‌ها
```

اندازهٔ دیتابیس: **۱۰۰۰ پرسنل، ۷۰۰۰ پرونده (۱۰۰۰ باز)، ۱۴۰٬۰۰۰ نمره،
۲۵٬۵۰۰ ردیفِ ممیزی** — یعنی سه سالِ یک سازمانِ هزارنفره.

> عددِ میلی‌ثانیه به ماشین بند است و در CI تکرارپذیر نیست؛ **شمارِ کوئری** به
> شکلِ کد بند است. به همین دلیل تست‌های رگرسیونِ این فاز شمارِ کوئری (و در یک
> مورد، شمارِ *ردیف*) را می‌سنجند و نه زمان را.

## چه چیزی واقعاً غلط بود

### جاروی شبانه، سه N+1 داشت و نه یکی

`--trace` فهرستِ ۶۲۵۱ کوئری را به سه منبع شکست:

| تعداد | کوئری | چرا |
|---|---|---|
| ۲۰۰۰ | `count(*)` روی `notifications` | `notify_once` برای *هر اعلان* یک بار dedup را می‌پرسید |
| ۲۰۰۰ | `select … module_settings` | بررسیِ ماژول برای هر اعلان، و `db.get` «ردیف نیست» را کش نمی‌کند |
| ۲۰۰۰ | `INSERT INTO notifications` | `_queue_outbound` برای گرفتنِ شناسه `flush()` می‌زد، پس هر اعلان یک رفت‌وبرگشت |
| ۲۵۰ | `select users … role = 'hr'` | صفِ مشترکِ HR در هر پرونده دوباره خوانده می‌شد |

نکتهٔ دومی از همه مهم‌تر است و در نگاهِ اول دیده نمی‌شود: ردیفِ `module_settings`
فقط وقتی ساخته می‌شود که مدیری سوییچی را دست بزند. یعنی **استقرارِ تازه — که
هیچ‌کس تنظیماتش را عوض نکرده — بدترین حالت را داشت**، نه بهترین را.

### داشبورد، جدولِ نمره‌ها را چهار بار اسکن می‌کرد

«پنج شاخصِ ضعیف» و «پنج شاخصِ قوی» در دو بخشِ فرم، چهار کوئریِ جدا بودند که
تجمیعِ زیرشان — اسکنِ ۱۲۰ هزار ردیف — در هر چهارتا یکی بود.

و یک لایهٔ دوم زیرش: `count(distinct …)`ِ سنجهٔ کوهورت، Postgres را به
**مرتب‌سازی** می‌بَرد نه هش، و آن مرتب‌سازی هر ستونی را که در `GROUP BY` باشد
با خودش حمل می‌کند. با `category` و `description` در گروه، ۱۲۰ هزار ردیفِ پهن
مرتب می‌شد و ۲۲ مگابایت روی دیسک سرریز می‌کرد:

```
Sort  … Sort Method: external merge  Disk: 22384kB   ← پیش
Sort  … Sort Method: external merge  Disk:  2592kB   ← پس (فقط دو شناسه)
```

همین الگو در `reports._summary_data` هم بود و همان‌جا هم رفع شد.

### نمای مدیریتی، برای دو عدد کلِ تاریخ را می‌کشید بالا

میانه و صدکِ ۹۰ِ «زمان چرخه» در پایتون حساب می‌شدند: یک ردیف به‌ازای هر
پروندهٔ نهایی‌شدهٔ تاریخِ سازمان، مرتب‌سازی در حافظه، دو عدد. برخلافِ بقیهٔ آن
صفحه هیچ سقفی نداشت — نه پنجرهٔ زمانی، نه دوره.

حالا `percentile_cont` در خودِ Postgres. **میانه دقیقاً همان عددِ قبلی است**
(فرمولِ قبلی هم برای تعدادِ زوج میانگینِ دو عضوِ میانی را می‌گرفت). **صدکِ ۹۰
ممکن است کسری فرق کند**: تعریفِ استاندارد بینِ دو عضو درون‌یابی می‌کند و
فرمولِ قبلی نزدیک‌ترین عضوِ موجود را برمی‌داشت. هر دو «صدکِ ۹۰»اند؛ این یکی
تعریفِ رایج‌تر است و با اضافه‌شدنِ یک پرونده نمی‌پرد.

## دو چیزی که *انجام نشد* — و عددش

### ۱. `stage_stats` در SQL تجمیع نشد

نقشهٔ راه این را خواسته بود. اندازه‌گیری تشخیص را عوض کرد. در یک اجرای
تفکیک‌شده — که سهمِ SQL و سهمِ پایتون را جدا می‌گیرد — از ۴۵۱ میلی‌ثانیه،
**۴۵ میلی‌ثانیه SQL بود و بقیه پایتون**:

```
 34.8 ms   select … audit_log … ->> 'status'
 10.2 ms   select … evaluation_records where created_at >= …
  1.6 ms   select … users where id in (…)
──────────
 45   ms   SQL  ·  ۴۰۵ ms پایتون
```

یعنی مسئله «کوئریِ بد» نبود، «حلقهٔ پایتونی» بود. (عددِ جدولِ بالا — ۵۲۱ →
۳۶۰ — میانهٔ پنج اجرای کاملِ `measure_hot_paths` است؛ این یکی یک اجرای
تک‌بارهٔ تفکیک‌شده. دو روشِ اندازه‌گیری، نه دو عددِ ناسازگار.)

انتقالِ آن حلقه به SQL یعنی بازنویسیِ ظریف‌ترین تابعِ آماریِ سامانه با توابعِ
پنجره‌ای: مدتِ ماندن از `lead()` روی لاگ، صاحبِ هر مرحله با `CASE` روی شکلِ
زنجیره، شمارشِ بازدیدِ دوم برای پرونده‌های برگشت‌خورده، و کنار گذاشتنِ ردیفِ
«تولد». سقفِ سودش هم روشن است: تجمیعِ ۳۲ هزار بازدید در SQL خودش زمان می‌برد،
پس خوش‌بینانه ۳۶۰ → حدودِ ۱۲۰ میلی‌ثانیه.

**تصمیم:** حدودِ سه‌برابر شدنِ یک پنلِ تحلیلی، در برابر ریسکِ آمارِ مدیریتیِ
بی‌صدا غلط. انجام نشد. به‌جایش سه چیزِ ارزان انجام شد و ۵۲۱ → ۳۶۰ رفت:

* فهرستِ ثانیه‌های ماندن → یک جمع (شمارنده‌اش از قبل بود)
* ستونِ صاحبِ هر مرحله یک بار به‌ازای هر *شکلِ زنجیره* حساب می‌شود، نه هر بازدید
* `EvaluationStatus(…)` از رشته، ده‌ها هزار بار، حذف شد

رشدِ این تابع از قبل سقف دارد (`stage_stats_window_days`، پیش‌فرض سه سال). اگر
روزی سازمانی چند برابرِ این بزرگ شد، نقطهٔ شروعِ کار همین‌جا نوشته است.

### ۲. ایندکسِ trigram برای جست‌وجوی ILIKE ساخته نشد

جست‌وجوی `%…%` روی `personnel` با هزار ردیف: **۲ میلی‌ثانیه**. و مهم‌تر از
عدد، شکلِ رشد: `personnel` با *تعدادِ کارکنان* بزرگ می‌شود و نه با گذرِ زمان —
یعنی جدولی است که اصلاً موضوعِ فازِ ۳ نیست. سازمانِ ده‌هزارنفره هم حدودِ ۲۰
میلی‌ثانیه می‌شود.

در مقابل، `pg_trgm` یک `CREATE EXTENSION` لازم دارد که دسترسیِ superuser
می‌خواهد — یعنی یک پیش‌نیازِ تازه برای هر استقرار.

**تصمیم:** انجام نشد. اگر روزی جست‌وجو روی جدولی لازم شد که واقعاً با زمان
رشد می‌کند، آن‌وقت دوباره سنجیده شود.

### ۳. ایندکسِ مستقلِ `created_at` ساخته *شد*

این یکی برعکس بود: امروز بی‌اثر و فردا گران. `ix_evaluation_records_status_created`
ترکیبی است و ستونِ پیشروش `status`، پس فیلترِ فقط-تاریخ از آن سودی نمی‌برد —
و «آمارِ مرحله‌ها» دقیقاً همان شکل را می‌زند.

```
Seq Scan       … actual time=1.463..1.743   ← پیش
Bitmap Index   … actual time=0.027..0.161   ← پس (پنجرهٔ ۶۰ روزه)
```

دو میلی‌ثانیه امروز چیزی نیست؛ ساختنِ ایندکس روی جدولِ شلوغِ تولید فردا،
کارِ دیگری است.

هر پانزده جهشِ آزموده‌شده (برگرداندنِ هر رفع، یکی‌یکی) قرمز شدند.

## ۳پ — لنگرِ زنجیرهٔ هش

عددِ پایه: `verify_chain` روی ۲۵٬۵۰۰ ردیف، **۱۱۵۷ میلی‌ثانیه و کاملاً خطی از
ابتدای تاریخ**. این هزینه روی *هر بار باز کردنِ صفحهٔ گزارشِ رویدادها* بود و
هیچ‌وقت کوچک نمی‌شد.

| مسیر | پیش | پس |
|---|---|---|
| بررسیِ تعاملی (`/audit-log/integrity`) | ۱۱۵۷ ms | **۳ ms** |
| بررسیِ کامل (جاروی شبانه، یا `?full=true`) | ۱۱۵۷ ms | ۱۱۵۷ ms |

بررسیِ کامل ارزان نشد و قرار هم نبود بشود؛ فقط از مسیرِ درخواست به پس‌زمینه
رفت. آنچه ارزان شد، هزینه‌ای است که کاربر منتظرش می‌ماند — و برخلافِ عددِ
قبلی، دیگر با سنِ سامانه رشد نمی‌کند بلکه با *فعالیتِ از دیشب تا حالا*.

**دامی که این فاز دورش می‌چرخد** یک بهینه‌سازیِ ساده‌ی «از لنگر به بعد بسنج»
می‌تواند تضمینِ اصلیِ لاگ را بی‌صدا خراب کند: هر دست‌کاری در ردیف‌های پیش از
لنگر برای همیشه نامرئی می‌شود، و نشانِ صفحه هم سبز می‌ماند. سه چیز جلویش را
می‌گیرد و هر سه تست دارند:

* لنگر فقط پس از یک راستی‌آزماییِ **کاملِ موفق** جلو می‌رود
  (`audit.record_full_verification` — تنها جایی که لنگر تکان می‌خورد)
* خودِ لنگر پیش از استفاده وارسی می‌شود: هشی که نگه داشته باید هنوز با لاگ
  بخوانَد، وگرنه پاسخ قرمز است
* شکستِ بررسیِ کامل ثبت *و اعلام* می‌شود — کشفی که به کسی نرسد کشف نیست

سیدِ `seed_load_test` زنجیرهٔ هشِ **معتبر** می‌سازد (با همان `compute_hash`ِ
خودِ سامانه)، پس همین دیتابیس برای سنجیدنِ این فاز هم به کار آمد.
