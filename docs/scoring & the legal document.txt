## Verified correct


- **compute_result arithmetic**: per-indicator weights applied to score *and* cap; absent-section redistribution normalizes over present sections with an explicit all-zero-weight fallback to simple mean; bonus clamped on the added amount so final ≤ 100; thresholds are half-open, input-validated ascending, last band > 100, so every value in [0,100] gets exactly one label. Structurally mirrored by `computePreview` (weights, redistribution, zero-weight fallback), with the one rounding-mode exception above.
- **Scheme versioning / mid-cycle activation**: `scoring_scheme_id` + `indicator_framework_id` stamped at creation on both the single path (`create_evaluation`) and the bulk path (`bulk_evaluation.execute`, one read per batch); `finalize_scoring`, `set_special_score`, and the detail payload all read `rules_for_record` (the record's own scheme); the frontend prefers `evaluation.scoring_rules` over `/api/config` (EvaluationDetailPage.tsx:78). Activation retires the previous scheme with a flush before inserting the new active row (`uq_single_active_scheme`), only drafts activate, drafts are the only deletable schemes, and creator≠activator is enforced *inside* `activate()` so both HTTP and copilot pass through it. The preview endpoint writes nothing, runs the real `compute_result`, and excludes records with deleted indicators.
- **Un-stamped-record fallback is effectively dead code**: the P1-04 migration seeds v1 as `active`, stamps every existing record, and `activate()` never leaves zero active schemes — so `rules_for_record`'s fallback to the *current* active scheme cannot fire on real data.
- **Server-side rule enforcement**: evidence and bonus rules are read from the record's own scheme, never from constants, at every write point; special-score is draft-only (row-locked), 403s non-scorers, and always lands in the audit log with old+new values; DB CHECKs back bonus ≥ 0 and bonus-needs-reason; `evidence_max_words` is enforced server-side, not just in the UI.
- **Hash/QR verification path**: one document per record (unique FK); archival is idempotent with `begin_nested` + IntegrityError fallback, and the download-racing-background-archival race is covered by a test; sha256 stored at archive time; the verify endpoint keys on a ~192-bit random token (sequential-code lookup is tested-rejected), 404s unfinalized records, is rate-limited 30/min, returns only non-sensitive fields plus the hash; the verify page displays the sha256 for comparison; production config refuses http/localhost `PUBLIC_BASE_URL`, so QR links are always https. I rendered the same snapshot twice — byte-identical, so the race loser being discarded can never yield two different hashes for one record.
- **Snapshot integrity**: built in `_before` at `ceo_finalize`; `apply_transition` refuses finalize without scores *and* without a snapshot on both HTTP and copilot paths; the backfill sweep skips snapshot-less records instead of fabricating a "today" document; deleted indicators render as «(شاخص حذف‌شده)» instead of 500-ing.
- **PDF security**: Jinja autoescape on (user-supplied escaping tested); the URL fetcher whitelists only the templates dir plus `data:` URIs; Jalali dates render in the org timezone, with the old UTC off-by-one-day bug locked out by a test asserting *local* time (the fixed version, not the bug).
- **Copilot workflow parity**: `advance_evaluation` delegates to the real endpoint functions with mirrored role guards (`_stage`/`_exact`), pinned by `test_ai_workflow_parity`; `hr_claim`'s non-transition role guard is duplicated in the tool; `apply_transition` re-runs `ensure_hr_may_handle` inside the service so the SoD guard is path-independent; `_run_ceo_finalize` runs background tasks inline so the document is actually built in the copilot flow.
- **Improvement-plan threshold pair**: `< improvement_plan_max_pct` used consistently in the eligibility query, `create_plan`, and the dashboard funnel (with the boundary case commented and aligned).
- **CI is real and reproducible**: drift check passed; backend ruff + **1035 pytest** green (5:45) on real PostgreSQL 16 with partial indexes and FOR UPDATE locking; launcher ruff + **89 tests** green; e2e (fresh DB → alembic head → setup → API scenario incl. mock-LLM copilot confirmations) green; frontend oxlint + **270 vitest** + tsc/build green.
