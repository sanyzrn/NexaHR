## Verdict — 3 lines


Ran everything: all four `ci-local.sh` jobs green on real Postgres 17 (backend ruff + **1035 pytest** in 5:50, launcher 89, frontend lint+vitest+build, e2e API scenario) plus `--check-drift`. ## Findings — severity | file:line | what breaks | how to reach it | fix


**1. HIGH | `app/services/ai/tools/framework.py:261-310` (create) and `:324-344` (activate) | The copilot drafts a scoring scheme that `SchemeInput` would reject, and a second user can then activate it — invalid rules become the org's active scoring scheme.** The HTTP path `POST /api/scoring-schemes` (`app/api/routers/scoring_schemes.py:103-135`) validates through `SchemeInput` (`app/schemas/scoring_scheme.py:24-64`): section weights must sum to exactly 1, `bonus_max_points ≤ 20`, `evidence_min ≤ max`. The tool builds the `ScoringScheme` row directly with raw model-supplied floats and none of that. Verified by execution: the tool accepted `general=0.9, specialized=0.9, bonus=50` (HTTP schema rejected the same payload with `bonus_max_points ≤ 20` and the sum≠1 error); a second user with `manage_scoring` then activated it through the tool (two-person rule satisfied, so `activate()` let it through) — it became the active scheme that stamps every new record. Concrete reach: HR-A (manage_scoring, AI writes on): "یک طرح با سقف امتیاز ویژه ۵۰ بساز" → confirm; HR-B activates via UI or copilot. Impact (verified against `compute_result`): the weight-sum violation is self-healing (`evaluation.py:244-248` normalizes by present-weight sum — so that half is harmless), but `bonus_max_points=50` raises the real cap: `validate_bonus` (`evaluation.py:185`) accepts up to the scheme cap, and `compute_result` (`evaluation.py:269-272`) adds `min(bonus, cap, 100−base)` — a base of 55 becomes final 100 ("تمدید ممتاز") instead of 75 under any HTTP-created scheme. Also `evidence_min > evidence_max` can be stored unvalidated; `validate_evidence` (`evaluation.py:148-159`) then demands ≥min and ≤max words for required scores simultaneously — an unsatisfiable window that 400s every submit under that scheme (code-derived; the stored-row and activation steps are execution-verified). Fix: have the tool delegate to the endpoint function like its sibling tools (`create_indicator`, `update_indicator`) do, or validate through `SchemeInput` before `db.add`; additionally validate in `activate()` since activation is the irreversible gate and the copilot reaches it directly.


**2. MEDIUM | `app/services/ai/tools/people.py:944-1022` (seat writes at 990-992; `resolve()` checks only `is_active` at 954-964) | The copilot seats any active user into any chain seat, skipping the role-sanity check the HTTP `PUT /access` enforces — stuck chains plus a personnel-visibility grant to the wrong account.** HTTP `upsert_access` runs `_ensure_active_user_with_role` per seat (`app/api/routers/evaluation_access.py:29-46, 90-94`): the user must exist, be active, **and** `may_act_at(user.role, seat_role)`. The tool omits it entirely. Verified by execution: copilot `set_evaluation_access` accepted seating an *employee*-role user as `unit_supervisor` (the HTTP guard function blocks the same input with 400 «نمی‌تواند در این مرحله قرار بگیرد»); immediately afterwards `_can_view_personnel` for that employee on the subject returned **True** (`personnel.py:102-122` trusts `EvaluationAccess` seats), so the employee now reads the subject's profile via the legitimate `GET /api/personnel/{id}`. Second consequence (same defect, from `_ensure_active_user_with_role`'s own docstring): the chain jams — `create_evaluation` (`evaluations.py:395-402`) requires the seat-holder himself to open the record and `may_act_at` fails for him, so the subject becomes un-evaluatable until HR fixes the chain by hand. Reach: HR with `manage_personnel` via one confirmed copilot sentence. Fix: call `_ensure_active_user_with_role(db, seat_id, expected_role)` for each non-None seat in the tool (and mirror the HTTP 400 on `unit_supervisor` for `is_manager` persons instead of silently nulling).


**3. MEDIUM | `app/services/ai/tools/evaluations.py:452-468` and `app/services/ai/tools/framework.py:444-470, 491-526 | The module switches are cosmetic on the copilot path for three tools — the exact failure class the codebase claims was fixed.** `ensure_module_enabled` is deliberately called inside endpoint bodies "so both paths pass through it" (`api/deps.py:208-215`, `services/authorization.py:104-117`) — but that guarantee only holds when a tool delegates to the endpoint *function*. These three call services directly: `invite_self_assessment` skips the `self_assessment` gate (`personnel.py:253`), `preview_bulk_evaluations`/`run_bulk_evaluations` skip the `periods` gates (`periods.py:376, 397`). Verified by execution: with `self_assessment=disabled` in `module_settings`, the copilot invite executed and created the invitation + notification (HTTP on the same state would 403); with `periods=disabled`, `run_bulk_evaluations` ran the full bulk pipeline end-to-end — for any personnel with a chain it would have opened evaluations while the org believes the feature is off. Contrast: `create_period` and `create_improvement_plan` do delegate and correctly inherit their gates. Fix: add `ensure_module_enabled(ctx.db, "self_assessment"/"periods")` at the top of the three tool bodies, matching the endpoints.


**4. LOW | `app/services/ai/tools/people.py:371-428 | The copilot `update_personnel` omits two endpoint guards: contract-date ordering and supervisor-seat clearing on the manager flag.** HTTP `PATCH /personnel/{id}` rejects `contract_end_date <= contract_start_date` after applying changes (`personnel.py:652-657`) and, when `is_manager` becomes true, clears the stale `unit_supervisor` seat from `EvaluationAccess` with an audit event (`personnel.py:672-686`). The tool does neither. Verified by execution for the first half: the tool stored `start=2025-01-01, end=2024-01-01` (HTTP rejects); for the second half (code-derived, same handler): via copilot, setting `is_manager=true` on a person whose chain still has a supervisor seat leaves the seat in place, so the next `create_evaluation` stamps the supervisor as first scorer and the record takes the full four-seat shape the manager flag is supposed to prevent, and which the UI flow makes unreachable. Fix: apply the same post-write date comparison, and clear/null-check the supervisor seat on `is_manager` transitions exactly as the endpoint does.


## Verified correct


- **Two-axis model.** `require_capability` / `require_role_or_capability` / `audit_log_reader` (`deps.py:153-244`) read capabilities from the DB per request — grant/revoke takes effect on the next request with no token-logic involvement; `require_roles` exact-match and `require_chain_stage`→`may_act_at` compose correctly for all three chain shapes; `hr` is deliberately outside `_CHAIN_RANK` (`workflow.py:497-523`) and `may_act_at` returns False for it on chain stages.
- **JWT + revocation.** `get_current_user` validates type, numeric `sub`, `is_active`, and `tv` (`deps.py:39-85`); the token's `role` claim is never trusted (role re-read from DB per request), so role changes are effective immediately. Password change (`auth.py:268-277`) and admin reset (`users.py:225-232`) both bump `token_version` + `revoke_all_for_user` + set `must_change_password`; separation does the same (`personnel.py:557-568`). Refresh validates type/jti/user/`tv` before `rotate_session`.
- **Refresh rotation.** Single-use jti with 60-second grace, reuse outside grace → `revoke_all_for_user` (`sessions.py:73-117`); revoked/expired/foreign jti treated as theft. Double-confirm of a pending action is a conditional-UPDATE claim → 409 (e2e step 12 exercised it).
- **Forced password change.** Server-side allowlist of exactly three paths inside `get_current_user` — not a frontend redirect; refresh is intentionally outside it so the user stays locked but alive.
- **Lockout + rate limits.** Lock checked *before* password verify (`auth.py:122-131`), per-username counter in shared DB, window reset, counter zeroing after lock, dummy argon2 verify for unknown usernames, purge sweep, HR notification with dedup, capability-gated `unlock` with audit. Login 10/min, refresh 30/min, verify 30/min, AI chat configurable. Production validators forbid default JWT secret, demo seed, `FORWARDED_ALLOW_IPS="*"`, localhost/insecure CORS and `PUBLIC_BASE_URL` (`config.py:188-256`).
- **Row-level visibility.** `scope_evaluations_for_role` is a true allowlist with explicit 403 fallthrough and is shared verbatim by list, `export.xlsx`, the copilot search tool, and the AI context builder (fail-to-empty for out-of-scope roles). The `hr_panel_is_shielded` ↔ `IS_SHIELDED_FROM_HR_PANEL` pair is consistent (both derive from `OPEN_STATUSES`); no shielded record can ever sit in `submitted` (all three submit transitions guard `not skips_hr_review`), so the HR queue cannot leak them. The `OPEN_STATUSES` ↔ partial-index predicate `status NOT IN ('finalized','cancelled')` pair matches, and `create_evaluation` has both the pre-check and the IntegrityError→409 path.
- **`ensure_hr_may_handle` coverage.** Present at every HR touchpoint (approve, return, cancel, extend, claim, handover, reassign, top-level comment, objection resolution, detail view, PDF download) *and* re-enforced inside `apply_transition` itself for HR-role transitions — the copilot path cannot skip it. `add_comment`'s earlier hole (official `hr_review` comment) is closed.
- **Copilot framework itself.** Registration fails closed (no scope declaration → import error); guard re-checked at execute and again at confirm; the write switch re-checked at execute independent of advertisement; risky actions only run from the confirmation point with fresh capabilities; audit arguments sanitized recursively for secrets.
- **Other pairs.** Backend `compute_result` ↔ frontend `computePreview` both normalize by present-section weight sum (spot-checked both sides). The scoring-scheme two-person rule lives inside the shared `activate()` service (`scoring_scheme.py:146`), so UI and copilot both pass it (my cross-user activation succeeded; the creator-self branch is in the shared code).
- **Public surfaces.** `/metrics`: 404 until a token is configured, constant-time compare. `/docs`, `/redoc`, `/openapi.json`: disabled in production. `/api/verify/{token}`: 192-bit `token_urlsafe` lookup (never the enumerable `evaluation_code`), finalized-only, 30/min, returns only name/unit/pct/recommendation/sha256. `/api/health/ready` exposes operational state only.
