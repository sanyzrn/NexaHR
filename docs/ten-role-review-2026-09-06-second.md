## ROLE 01 — Authz & Session
### Verdict
The two-axis model is consistently enforced: roles gate chain position, capabilities gate administration, and every guard I traced is reachable from both the HTTP path and in-body calls. Forced-password-change is a server-side allowlist, not a UI redirect; `/metrics` is token-gated and `/docs` is production-disabled. Two session weaknesses found, neither an open door.
### Findings
- **MED | `backend/app/services/sessions.py:87-104` | Concurrent refresh double-rotates one session, so reuse detection never fires.** `rotate_session` reads the `AuthSession` row without `with_for_update`; two parallel `POST /api/auth/refresh` with the same cookie both read `rotated_at IS NULL`, both create a child session, and both return 200. Reach: attacker with a stolen refresh token refreshes in the same instant as the victim → two live session branches exist, the "reuse = theft → revoke all" invariant only holds for sequential reuse, and the theft goes undetected. Fix: `select(AuthSession).where(jti == ...).with_for_update()` in `rotate_session` (the row lock serialises the rotate, the second request then sees `rotated_at` and hits the grace/revoke path).
- **LOW | `backend/app/api/routers/auth.py:240-247` | `change-password` is the only auth endpoint with no rate limit.** `login` (110) and `refresh` (186) are `@limiter.limit`-decorated; change-password is not, and the login-guard lockout does not apply to it. Reach: with a stolen access token (30-minute TTL, `config.py:30`), an attacker gets *unbounded* `verify_password` calls against `current_password` — each one also burns ~100 ms server CPU. Fix: `@limiter.limit("10/minute")` + count failures toward the login guard.
### Verified correct
`get_current_user` (`deps.py:39-85`): type check, numeric-sub hardening, `tv` revocation, inactive check, allowlist-forced-change — all server-side. Dummy-hash verify on unknown username kills the timing oracle (`auth.py:52,157`). Lockout is checked *before* verification (`auth.py:121`), counted atomically via `on_conflict_do_update` + `FOR UPDATE` + `populate_existing` (`login_guard.py:76-93`), and zeroed after lock so post-lock attempts get a full window. Refresh cookie: HttpOnly, SameSite=strict, path-scoped to `/api/auth`, `secure` in production. Capability guards (`require_capability`, `audit_log_reader`) genuinely consult the DB per request; the last-grantor rule protects `manage_capabilities` (`administration.py:185`). `delete_user` refuses any account with audit history (`users.py:360-370`). Self-claim of `hr_claim`/`reassign`/`cancel`/`extend`/`handover` all funnel through `ensure_hr_may_handle`/`ensure_may_administer`.
### Could not check, and why
Multi-worker behaviour of the in-process rate-limit store (documented single-instance decision); real brute-force economics against argon2 parameters.
