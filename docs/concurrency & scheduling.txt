## Verdict — 3 lines
The concurrency backbone is genuinely solid: every workflow write path takes `SELECT … FOR UPDATE`, the AI double-confirm uses an atomic conditional-UPDATE claim, the audit chain serializes on `pg_advisory_xact_lock` under READ COMMITTED with a single writer, and the scheduler's session-level leader lock is held and released on a dedicated connection (M-10 is really fixed). I ran all four CI jobs on PostgreSQL 16 (1036 backend tests + launcher + frontend + e2e, all green, `--check-drift` clean) and then attacked the edges with interleaved-transaction probes against a live DB. What survived the probes as real defects: the per-account brute-force lockout counter, the delivery queue's candidate window, and three straggler read-decide-write paths that never got the row-lock treatment the rest of the repo got.


## Findings — severity | file:line | what breaks | how to reach it | fix


**1. HIGH — `backend/app/services/login_guard.py:44-75` (`record_failure`), consumed at `backend/app/api/routers/auth.py:133-150` (`_fail`) — per-account lockout is defeated by parallel requests, and the first-failure insert 500s the login endpoint. VERIFIED by probe.**
- What breaks: (a) *Lost update.* `row = db.get(LoginAttempt, username)` (line 53) → `row.failed_count += 1` (line 63) is a Python-side read-modify-write with no `FOR UPDATE`. Two concurrent failures both read count *n*, both write *n+1* — one failure silently vanishes. (b) *Insert race.* Two concurrent failures for a username with no row yet both take the `row is None` branch (55-56); the second `flush` blocks on the first's uncommitted INSERT and then raises `UniqueViolation` out of `record_failure`. `_fail` (auth.py) has no `IntegrityError` handler, so it surfaces as an unhandled 500 on `POST /api/auth/login` instead of a 401.
- How to reach it: sync FastAPI endpoints run in a threadpool, so requests are truly parallel. Attacker sends a guess flood in parallel batches: with threshold `login_max_failed_attempts`, each wave of N parallel bad-password requests counts ≈1 instead of N, so the P0-04 per-account lockout — the *only* per-account defense, since the per-IP limiter is in-process and per-IP — never trips under full parallelism. Probe: two interleaved `record_failure` transactions (T1 read/increment/flush → T2 read → T1 commit → T2 increment/flush/commit) left `failed_count=1` after two failures; the insert variant reproducibly escaped `UniqueViolation`.
- Fix: make the counter atomic in SQL — `INSERT INTO login_attempts (…) VALUES (:u, 1, :now, :now) ON CONFLICT (username) DO UPDATE SET failed_count = CASE WHEN last_failed_at < :window_start THEN 1 ELSE login_attempts.failed_count + 1 END, … RETURNING failed_count, last_failed_at` (and derive the lock in the same statement), or keep the ORM shape but `db.get` with `with_for_update()` first. Either way, also catch `IntegrityError` in `_fail` so a lost race degrades to a 401, never a 500. This also fixes the lockout-notification double-fire, since only the request whose atomic increment crosses the threshold will see it.


**2. MEDIUM — `backend/app/services/delivery.py:133-141` (`run_delivery_sweep`): the `batch*4` candidate window plus Python-side due-filter starves fresh pending rows behind failed rows in backoff. VERIFIED by probe.**
- What breaks: candidates are `SELECT … WHERE status IN ('pending','failed') ORDER BY created_at LIMIT batch_size*4` (lines 133-140), and the backoff filter `_is_due` runs *after* the limit (line 141). When the oldest `batch*4` rows are all `failed` and mid-backoff, every tick reads the same window, filters all of them out, and sends nothing — newer `pending` rows that are immediately due sit beyond the limit and are never even considered. The 4× overfetch was meant to compensate for exactly this and doesn't.
- How to reach it: defaults (batch=50 → window=200, base=5 min, max 5 attempts). An SMTP/SMS outage that covers ≥200 enqueued outbound rows (one bulk-finalize day notifies scorer + subject per record; SLA/contract sweeps add more) leaves ~200 `failed` rows whose next-due times are 5–80 min apart, needing up to ~155 min to abandon. After the provider recovers, each 5-min tick picks the same 200 not-due rows → `sent=0` while action-required notifications (approval-due, SLA, `evaluation_finalized_self`) pile up un-sent until enough old rows abandon; with a sustained backlog this is indefinite. Probe: 40 failed-not-due rows with `delivery_batch_size=10`, 5 fresh pending rows → `run_delivery_sweep` returned `{'sent': 0, …}` and the pending rows stayed `pending`.
- Fix: push due-ness below the limit — filter in SQL, e.g. `WHERE status IN ('pending','failed') AND (last_attempt_at IS NULL OR last_attempt_at + make_interval(mins => :base) * power(2, attempts - 1) <= :now)` (or a simpler precomputed `next_attempt_at` column set when `attempts`/`last_attempt_at` are written), and drop the 4× overfetch. Ordering by `(last_attempt_at IS NOT NULL), created_at` is a lighter variant but still misbehaves at the boundary.


**3. LOW-MEDIUM — `backend/app/api/routers/improvement_plans.py:378-400` (`complete_plan`), `403-423` (`cancel_plan`), `329-375` (`update_plan`): read-decide-write on plan status without the row lock this repo applies everywhere else.**
- What breaks: `_get_plan_or_404` (51-55) is a plain `db.get`. Both terminal endpoints do `if plan.status != open: 400` → set status → `log_event` → commit with no `with_for_update`. Two concurrent completes double-write `improvement_plan_completed` — permanent duplicate events in a hash-chained, append-only audit log that this org treats as evidence. Mixed complete+cancel (two HR admins, or a double-fired button in one tab racing the other admin) both pass the open-check and the last commit wins: the plan ends in an arbitrary terminal state while the chain records two contradictory decisions.
- How to reach it: role `hr`, any plan with `status=open` on the screen of two HR users; both click a terminal action in the same instant. No lock serializes the checks; READ COMMITTED lets both read `open`.
- Fix: match the repo's own pattern — fetch with `with_for_update()` for write endpoints, or claim terminally like `confirmations._claim_for_execution` does: `UPDATE improvement_plans SET status=:s, completed_at=:now WHERE id=:id AND status='open'` and 409 when `rowcount=0`.


**4. LOW — `backend/app/services/sessions.py:73-117` (`rotate_session`): refresh rotation is read-then-write with no row lock — a concurrent refresh forks the token family.**
- What breaks: `session = db.scalar(select(AuthSession).where(jti == …))` (line 87) reads `rotated_at`; two requests carrying the same still-valid cookie both see `rotated_at IS NULL`, both pass the reuse check, and both `create_session` + set `rotated_at` → **two** live successor sessions where the rotation threat model guarantees one. The practical casualty is theft detection: a stolen token refreshed *concurrently* with the owner's own refresh produces a forked family, so neither successor's later reuse ever hits `RefreshReuseError → revoke_all_for_user`.
- How to reach it: any client double-fires `POST /api/auth/refresh` (two tabs mounting, retry-after-timeout), or attacker + owner refresh within the same few hundred ms; both get valid cookies.
- Fix: `select(AuthSession …).with_for_update()` on line 87 (second waiter blocks, then re-checks `rotated_at` and takes the grace path), or claim with `UPDATE auth_sessions SET rotated_at=:now WHERE jti=:j AND rotated_at IS NULL` before creating the successor, 409/401 on `rowcount=0`.


**5. LOW — `backend/app/api/routers/ai.py:454-471` (`chat`): the daily quota is count-then-act with no serialization — parallel sends exceed the limit.**
- What breaks: `used = COUNT(AiMessage … created_at >= now-1day)` (454) is compared against `daily_limit` (466), but the counted row for the current message is only inserted after the turn completes. N parallel chat requests all count the same `used` and all proceed, so the user-visible "سقف روزانه" is overshootable by its own client's parallelism (same user, two tabs, or a double-fired send).
- How to reach it: any user with a quota (non-None `resolve_daily_limit`), sending ≥2 chats in parallel when `used == limit-1`.
- Fix: lowest-friction is to insert the user `AiMessage` (already flushed at line ~480) *before* the quota check and count it including itself; or keep a per-user counter row updated atomically. Documenting the quota as soft would also be defensible — but then say so in the message.


## Verified correct
- **`with_for_update` coverage on the evaluation chain is real, not just documented.** All twelve write endpoints in `evaluations.py` (submit, hr-approve, deputy-approve, ceo-finalize, return, cancel, extend-submission, hr-claim, hr-handover, resolve-objection, reassign, upsert-scores/evaluator-comment/special-score) fetch via `_get_record_or_404_for_update` (112-130, `of=EvaluationRecord` for the outer-join caveat). `me.py` self-assessment write locks too (290-317), and `personnel.py` separation locks the open record before cancelling it (510-535) — the exact "CEO finalizes while HR processes the departure" interleave resolves to a clean 403 instead of un-cancelling a signed document. Double-click double-submit: second request sees the post-commit status and gets a clean 400/403; the `upsert_scores` auto-save racing a `submit` is serialized so scores can never land after `finalize_scoring` computed the result.
- **AI double-confirm is properly atomic.** `confirmations._claim_for_execution` (39-61) does `UPDATE ai_pending_actions SET status='executing' WHERE id=:id AND status='pending'`, checks `rowcount`, and **commits before running the tool** — exactly the fix needed because tools commit internally mid-run (which would release a row lock). Parallel confirm/reject → 409; HTTPException handler rolls back partial writes then records `failed` (H-3). `reject` uses the same conditional-UPDATE claim.
- **Copilot path has no lock/guard bypass.** `tools/evaluations.py` calls the real endpoint functions (`ep.submit_evaluation`, `ep.hr_approve`, `ep.ceo_finalize`, `ep.create_evaluation`, `add_comment`…) with a real Pydantic payload — so the row lock, `ensure_hr_may_handle`, `finalize_scoring`, snapshot/verify-token creation, and the mid-function commits all run on the copilot path too; the `_ADVANCE` role table re-derives `require_chain_stage`/`require_roles` parity and is pinned by `test_ai_workflow_parity`. `hr_claim` needed that table and has it.
- **Audit chain.** `pg_advisory_xact_lock` (audit.py:85) is taken *before* reading `prev_hash`; the app's sessionmaker sets no isolation override, so READ COMMITTED gives the lock-waiter a fresh snapshot that sees the previous append → no forks. `log_event` is the sole constructor of `AuditLog` (grep-verified across `app/`), and a rolled-back transition (e.g., a failed finalize) rolls its chain row back with it, leaving no gap. `trg_audit_log_append_only` and `trg_audit_log_no_truncate` verified present in the live migrated DB, not just in migrations e8f4b127d905/c1e5a9d2f70b. Advisory keys `_CHAIN_LOCK_KEY` and `_SWEEP_LOCK_KEY` are distinct and stable.
- **Double-open protection.** `create_evaluation` pre-checks + relies on `uq_open_evaluation_per_personnel` and converts `IntegrityError` into a 409 that carries the winner's id (449-468); `bulk_evaluation.execute` wraps each record in `begin_nested` and reports `blocked_conflict` honestly instead of failing the batch.
- **Document idempotency.** `archive_final_pdf` (documents.py:29-87) is check → render → INSERT inside `begin_nested`, with the unique FK on `evaluation_documents.evaluation_record_id`; the three concurrent creators (background task after ceo-finalize, `GET /summary.pdf`, `run_document_backfill_sweep`) converge on one row, and the IntegrityError loser re-reads instead of 500ing.
- **Scheduler lock.** `run_sweeps_once` holds `pg_try_advisory_lock` on a dedicated pooled connection, unlocks on that same connection before closing it (the M-10 fix is correctly built, and the session-level lock survives the mid-run commits on the *other* connection); `skipped_locked` is recorded in `scheduler_runs`; the in-process loop is strictly sequential (`await` → sleep, no overlap); the manual endpoint `POST /api/admin/run-scheduled-jobs` shares the same lock and 409s instead of double-sweeping — so sweep-side `notify_once` check-then-insert dedup has no concurrent same-key writer.
- **Delivery mechanics.** `attempts`/`last_attempt_at` are stamped *before* `channel.send` (no hot-retry loop on a crashing channel), retryable vs permanent failures are split, channel-missing rows are left untouched, and the whole batch is at-least-once (crash between send and commit → one duplicate on the next tick, acceptable for email/SMS). `evaluation_code` comes from a PG sequence — no duplicate-code race; `verify_token` is set once under the row lock in `ceo_finalize._before`.

- **The PDF archival path was never executed** — WeasyPrint's native libraries aren't installed in this environment, so `run_document_backfill_sweep` and `archive_final_pdf` ran as no-ops (and the e2e scenario is API-only); the SAVEPOINT race logic there is verified by reading only.
